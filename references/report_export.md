Runs after Phase 6.5 (verify), before Phase 8 (decision walkthrough). A run
produces **two versions** of one study:

| Version | For whom | Files |
|---|---|---|
| Human | the client of the research and those they forward it to: with no skill context | `<date>_<slug>.html` — one page for 5–7 minutes; `<date>_<slug>_full.pdf` — the full study with the evidence base and a source index; `_full.docx` — the same for edits |
| Technical | the agent, the specialist, a future `update` | `memo.md`, `<date>_<genre>.md` (+ `.html` with margin notes), `claims.csv`, `numbers.csv`, `sources/`, `evidence/`, `.verify/` |

Plus a `README.md` in the run folder — a map of «what a human should open, what lies there for
the agent». It is generated by the build; a README written by hand is not overwritten.

```bash
uv run scripts/build_report.py <run>                    # both versions + the map
uv run scripts/build_report.py <run> --formats html,pdf # the human one without DOCX
```

## The human version: readout.md

It is written **separately** from the technical report, not derived from it by cutting out
codes: «CL13 contested low, fork 2 fires partially» does not become comprehensible by
swapping the words. The order:

1. Write `readout.md` by the template below from the technical report and `memo.md`.
   The claims are the same ones that passed verify; no new facts appear here.
2. Fill in the `evidence_kind`, `plain`, `detail` columns in `claims.csv` (see
   `source_scoring.md`) — the PDF evidence base is assembled from them.
3. **Run `readout.md` through a humanising pass** (available in the environment — mandatory).
   The humaniser does not touch quotes, numbers, `[sNN]` or heading attributes.
4. `build_report.py` — the build.

```markdown
---
title: "Short title-question"
question: "The question in full, as a human would ask it"
genre: custom        # qa | explainer | decision | landscape | validation | custom
date: 2026-09-29
---

## Answer
2–3 sentences: what was found out and what to do about it. The last line — «Confidence: high | medium | low — and why».

## Do
- An action — and why [sNN].

## Don't
- What not to do — and why [sNN]: what the data argues against.

## What would change the decision
- **If** <an observable event>, **then** <an action>. A deadline, if there is one.

## Findings          ← the core of custom; other genres have their own, see the table below
### <The claim in full, not the topic> {.high claims="CL1;CL4"}
2–4 sentences: what exactly was found and why it matters for the question [s01][s62].
Where it is a forecast or our own frame — say so.

## What speaks against
### <The counter-argument as a claim> {.contested claims="CL6"}
Who holds it and why [s67].

## What we don't know
- A gap — and the cheapest way to close it (a measurement, a quote, an interview), with a cost in hours or money.

## Glossary            ← only if a term is indispensable
```

### Frame + core by genre

The template above is the frame and core of `custom`. **The frame is common to all genres** — «Answer»,
«Do», «Don't», «What would change the decision», «What we don't know» and (except validation)
«What speaks against». The frame is checked by `build_readout.py` (`lint_structure`).
This is the trust layer: any report reads the same way. **The core is per genre**: the thing
the reader opens a report of that genre for. One template for all genres would rewrite
a market map into five «findings» and lose the table of options — verified on the Karkas v4
run: the most useful part disappeared, the table of candidates.

The genre is taken from `genre:` in the frontmatter, otherwise from the name of the technical report.
The core is placed **between** «What would change the decision» and «What speaks against».

| Genre | Mandatory core | Cards | Label on the card |
|---|---|---|---|
| decision | `## Варианты` — an **options table** by 3–6 criteria (scored in words, not points), then `### Вариант` for each: when it fits, when it does not, the main risk; the last line — a recommendation with a condition | «Variant N» | not mandatory |
| landscape | `## Карта`: `### Категория` → `#### Игрок` (who, what they do, for whom, price, a fresh signal); `{.key}` — the player gets onto the HTML page, the rest only into the PDF. Then `## Где пусто` and, optionally, `## Что меняется` | «Player N» | not mandatory |
| validation | The verdict — in the «Answer». `## Доводы за`, `## Доводы против` — cards with the **strength of the argument** `{.strong|.moderate|.weak}`; `## Что изменило бы вердикт`. There is no separate «What speaks against»: the arguments against are already in the core | «For N», «Against N» | the strength of the argument |
| explainer | `## Словарь` **before** the core, if terms are needed; `## Как устроено` — a diagram (`{{fig:…}}` or a description), the steps as a numbered list, `### Где обычно путают`. `###` here are subsections, not cards | — | — |
| qa | `## Вопросы`: `### Вопрос, как его задали?` → a short answer | «Question N» | confidence |
| custom | `## Находки` — the template above | «Finding N» | confidence |

The cards of «What speaks against» in all genres are «Against N» with a confidence.
Every card of the core and of the frame must have at least one `[sNN]`.

Confidence is the heading class: `.high` «reliable», `.medium` «likely», `.low`
«weak», `.contested` «opinions diverge». `claims="…"` links the card to
items of the evidence base («→ option 2»); the attribute is not visible to the reader.

**The build fails (strict) if** the human-facing text contains ledger codes (`CL`,
`H`, `R`, `N` with a number), the skill's service words (fork, contested, triangulated,
faithfulness, credibility, claim, ledger); a section of the frame or of the genre core is missing; the
decision has no options table; the landscape has no players on the map; a card has no
mandatory label or not a single `[sNN]`; a link points to a non-existent source.

### What lands where

- **HTML page:** title → answer → what would change the decision → the genre core → against →
  what we don't know. In landscape — only the key players (`{.key}`). At the end a collapsed block «For the specialist»: how it was conducted and
  the source index. A source number in the text is a superscript link; on hover
  the title, author and date.
- **PDF (the full study):** the same + **the evidence base by type of material**
  (numbers as a table, facts as a chronology, studies, positions, products, cases, norms,
  «not found») + «How the study was conducted» with the technical summary of the F10 check +
  the source index: one line per source — who, when, type, reliability
  in words, which items of the base were taken from it. There are deliberately no verbatim quotes in the PDF:
  they confuse, and they live in `sources/` and `evidence/`.

## The technical version

It is assembled into HTML with margin notes; PDF and DOCX now carry the human version.
The register is **a report of 15–20 pages for one decision.** Not a reference work: a table of contents,
section versioning and delta markup are deliberately absent here. A living digest of 50+
pages is a different layout, not a setting of this one.

`memo.md` **is not merged into the document** and stays a separate page. No one reads
twenty pages before a decision; if the memo is dissolved inside, exactly the
part that will certainly be read is lost.

## What the build does beyond conversion

| Step | Why |
|---|---|
| Figures from the ledger | A number without a row in `numbers.csv` cannot be drawn — the build fails |
| Margin notes | The source is visible without leaving the paragraph (Tufte's apparatus) |
| Resolving `[sNN]` | A broken link fails the build: in 20 pages it is not found by eye |
| Source appendix | Generated from `sources.csv`, including `access` and `fetch_tier` |
| Mermaid diagrams | The ```` ```mermaid ```` fence is cut before pandoc and drawn by `mmdc`; a diagram the renderer did not take fails the build |

Three separately maintained files are three diverging reports, not one in three
forms. That is why the source is one: markdown plus CSV.

## figures.csv

It lies in the run folder next to `numbers.csv`. One row — one figure.

| Field | Value |
|---|---|
| `fig_id` | `F1`, `F2`, … — the figure is inserted into the text by this token `{{fig:F1}}` |
| `form` | `bar` · `slope` · `share` · `dot` · `line` |
| `numbers` | `num_id` separated by `;` — **only from `numbers.csv`** |
| `labels` | series labels separated by `;`, by position; empty — `num_id` is taken |
| `notes` | a note on a series without a value (e.g. «the feed is dead (404)») |
| `title` | mandatory: a figure without a title is unreadable |
| `subtitle` | a refinement — what the slice is, which sample |
| `caption` | the caption under the figure: what is visible here, not what is drawn |
| `legend` | the legend label for `dot`; by default the unit of measurement |

In the text: `{{fig:F1}}` on a separate line. The «Fig. N» numbering follows the order of rows
in `figures.csv`, not the order in the text.

## Choosing the form

The form is dictated by the work the data does, not by taste. There is deliberately no pie in the set:
shares are not compared by angles.

| What the data does | Form | Why |
|---|---|---|
| A magnitude by category | `bar` | Length compares more accurately than angle and area |
| A change between two points | `slope` | The slope reads instantly; two columns do not |
| A part of a whole | `share` | The frame shows the denominator: a share without it lies |
| A comparison across objects | `dot` | Compact, and an empty value shows as empty |
| A series over time (N8) | `line` | ≥3 points, only the ends are labelled |

**The absence of data is drawn as a dashed line, not as zero and not as a gap.** An empty row
in `value` gives a dashed tick with the text from `notes`. Zero is the statement
«we measured and got zero»; a gap is «we are silent about it». Neither equals
«there is no data».

## Provenance in the figure

The footer of every figure is assembled from the ledger, not written by hand: the sources `[sNN]`,
the `as_of` range, and the formula for `derived`. The reader recomputes a derived number
without leaving the figure.

`check_number_arithmetic.py` already checks that `derived` agrees with `formula`, and that
`share` groups give 100 ± 0.5. A figure built from the ledger inherits this
check for free.

## Footnotes

The author writes ordinary markdown footnotes:

```markdown
The share doubled [s04].[^base]

[^base]: The 2025 base was recalculated on the 2026 methodology — comparability is limited.
```

For HTML and PDF the footnote moves to the margin opposite its line. For DOCX it stays
a footnote: **there are no side margins in Word**, and flattening it into a paragraph in the middle of the text would be
worse. Hence the rule: DOCX is the format for edits and sign-off; people read the PDF and the HTML.

A mismatch of «N footnotes in the document, M moved» fails the build. A silently lost
footnote is indistinguishable from its absence: the text looks whole while the source of the claim
is gone.

## Layout

The direction is **e-ink/paper** (`assets/report.css`), chosen for the register «reading
long text»: tinted paper `#f5f2ea`, ink `#2b2926` (contrast ~12:1,
not maximal — maximal is tiring), a 62-character column, a serif Charter.
Zero shadows, zero gradients. **The hierarchy rests on type size and vertical rhythm:
take the colour away — the structure will not change.**

The figure palette `#0072a8 · #c9560c · #8a4fb0` was run through
`dataviz/scripts/validate_palette.js` on paper and on a dark ground — six
checks PASS. Green was excluded deliberately: the green↔rust pair gave
CVD separation of 3.9 against a threshold of 8.

Changing the palette — only after running the validator again. It is not picked by eye: the first
attempt failed two checks out of six.

## Mermaid diagrams

The blocks E13 `flow-diagram` and M9 `network-graph` are written as an ordinary fence in the
report text. Then comes the pipeline:

1. `tokenize` cuts every fence before pandoc and puts `{{dia:DN}}`. Without this
   pandoc carries the diagram into `<pre>` as code.
2. `mmdc` draws SVG in the e-ink theme from `assets/report.css` (the base colours are set in
   `mermaid_figures.THEME`, and are not picked in each diagram).
3. HTML and PDF get the SVG inline, DOCX — as an image; the caption is taken from
   `%% caption: <text>` inside the fence.

**The numbering is separate — «Diagram N», not «Fig. N».** A figure has a row in
`numbers.csv`; a diagram does not and cannot: a diagram is responsible for structure, not for
a number. A shared counter would mean a «Fig. 4» reference to a picture with not
a single verifiable value behind it.

**There is no limit on the number of nodes.** There was one while diagrams were drawn in ASCII
by hand. A diagram should be split by meaning — when two different questions have landed in one picture —
and not by the count of nodes.

**The id of the root `<svg>` is unique per document** (`-I dia-DN`): mermaid scopes its
styles by id, and the default `my-svg` on two diagrams means that the styles of the second paint
the first.

## Dependencies

| What | For what | If missing |
|---|---|---|
| `pandoc` | all formats | the build fails |
| `chrome-headless-shell` from `~/.cache/puppeteer` (`npx puppeteer browsers install chrome-headless-shell`; the newest version is taken, otherwise `chrome-headless-shell`/`chromium` from `PATH`) | PDF, diagram rendering | the PDF is skipped, HTML and DOCX are still built |
| `mmdc` + `puppeteer` | Mermaid diagrams | there is a fence → the build fails; with `--no-strict` the diagram stays as code in the text |

LaTeX is not needed: the PDF is printed by a headless browser from the HTML. Chromium is already installed for
the Phase 4.2 fetch ladder.

The diagram renderer is installed once and **without a second Chromium** — it takes the same
binary that prints the PDF:

```bash
PUPPETEER_SKIP_DOWNLOAD=1 npm i -g @mermaid-js/mermaid-cli puppeteer
```

`puppeteer` is mandatory here as a separate line: in `mermaid-cli` it is a peer dependency
and is not pulled in by itself — without it `mmdc` fails with `ERR_MODULE_NOT_FOUND`.

## What is not here

- A table of contents and section versioning — the register is wrong, see above.
- A dark theme for printing: the document is printed on paper.
- Automatic choice of form by the data. The author chooses the form — that is a substantive
  decision, not presentation.
