## Why

The skill had two layers out of three. **Raw** — `sources/NN.md` in the run and `~/.knowing/state/observations.jsonl`. **Skills** — `references/channels.md` and `api_sources/`, which `promote_candidates.py` edits behind an honest gate (3 wins in 3 DIFFERENT runs + a live endpoint + demotion by DEAD_STRIKES). Between them there was nothing, and the consequence is simple: knowledge of **where to look** accumulated, but not of **what was found out**.

What followed from this:

- one source in two researches — two unconnected files, credibility computed from scratch;
- a claim triangulated in June is invisible to a run in August;
- two runs can reach opposite conclusions, and no one will notice;
- an `application.md` with the status `deferred` wrote off the whole run.

The wiki closes exactly this. It survives the rejection of a report: knowledge is separated from the verdict on it.

## Where it lives

`~/.knowing/research/wiki/` — global, not in the project folder. Research folders live per project (`research/`, `06_Деск-ресёрч/`, `~/knowing/`), and a wiki inside a project would fragment exactly what must accumulate. The precedent already exists: `applications_ledger.csv` and `state/` are global too.

```
wiki/
├── INDEX.md              # navigation, regenerated by every ingest
├── sources/<slug>.md     # one page = one canonical URL/DOI
├── entities/<key>.md     # company / tool / method
├── claims/<c-id>.md      # one OBSERVATION of a claim (runs are not merged)
└── .wiki/
    ├── sources.csv · entities.csv · claims.csv   # registries, pages are rendered from them
    └── pairs.jsonl                               # verdicts on pairs, append-only
```

## The three join keys — and why the third is built differently

| Layer | Key | Nature |
|---|---|---|
| Sources | canonical URL, DOI outranks URL | mechanical |
| Entities | collapsed name + aliases | semi-mechanical |
| Claims | `(run, claim_id)` — **not text, not meaning** | an observation, not an entity |

Sources merge automatically: `arxiv.org/abs/X`, `/pdf/X`, `/html/Xv2` are one page. The scheme, `www.`, utm parameters, the fragment and the trailing slash fall away.

Claims **are never merged**. Deciding that two sentences from different runs are «the same claim» is a semantic judgement, and an error in it manufactures a contradiction out of nothing: a broken measurement → a false diagnosis. So claim identity is not inferred here. There are only edges between observations, each with a verdict and a trace in `pairs.jsonl`. A wrong edge is one line to repair; a wrong merge is irreversible.

`claim_uid = (run, claim_id)` deliberately **does not include the text**: 5.7 builds the pairs before synthesis, ingest writes after it, and in between the wording gets edited (remediation, a caveat restored, an overclaim softened). A hash over the text would move the id and hang all the pairs.

## Phase 5.7 — reconciliation

It runs **before** synthesis, not after. A divergence from an earlier research must get into the report; noticing it in phase 7 means noticing it too late.

```bash
python scripts/wiki_pair.py build --research-dir <root>/<slug>
```

**Pre-filter (mechanical).** A pair is formed at all only if the claims share an entity AND a comparable slot: a matching unit of measurement or enough overlap of content tokens (Jaccard ≥ 0.34 after the entity name is dropped). A shared entity is not enough: «Postgres is popular» and «Postgres 16 supports logical replication» have nothing to compare.

**Auto-verdicts (before the model).** Every branch here is a known way to invent a contradiction:

| Situation | Verdict | Why it is not a conflict |
|---|---|---|
| both sides with numbers, `as_of` more than 180 days apart | `superseded` | the number is simply newer — a version, not a dispute |
| the units do not overlap (40% vs 40 million) | `different-claim` | they measure different things |
| the scope qualifiers differ (US/EU, median/mean, enterprise/free, year) | `different-claim` | they speak about different things |

Only what survived the prescreen reaches the adjudicator. No confidence of the model will turn an outdated price or another region into a disagreement — they simply have no path there.

**Adjudication.** The remaining pairs live in `<run>/.verify/wiki_pairs.json`. The verdict is one of four: `same-claim-agree` · `same-claim-conflict` · `different-claim` · `unknown`. `unknown` is quarantine: not agreement, not conflict, it does not go into the report, and after 90 days the linter raises it as debt.

```bash
python scripts/wiki_pair.py record --research-dir <root>/<slug> --verdicts <file.json>
```

`record` **rejects the whole batch** if a conflict is filled in one-sidedly. A conflict without a second `as_of` is indistinguishable from an outdated number, and without second roots — from one source quoted twice. Such a «conflict» would enter the report as a finding it did not earn.

**What to do with a confirmed conflict.** It is not a defect of the run. Two well-founded positions diverge because the question is contested — that is what `dissent` in phase 5 already exists for. One thing is new here: the divergence became visible BETWEEN runs, not only inside one. Both positions go into the report with a justification of the choice, `confidence` no higher than `medium`, and if there is no arbiter — `contested`.

**The limit.** Above `MAX_ADJUDICATED = 40` pairs — a cut by the freshness of the counterpart, and it is **stated out loud** in the output and in the report. Unchecked pairs ≠ absence of contradictions.

## Finish-up — writing

```bash
python scripts/wiki_ingest.py --research-dir <root>/<slug>
```

Deterministic, with no model calls, **at any depth**. A shallow run costs exactly zero for ingest, and its sources are reusable no worse than a deep run's; a gate on depth would deprive the wiki of most of its input and leave 5.7 without a base for comparison.

It writes the receipt `<run>/.verify/wiki_ingest.json`, and `validate_phases.py` requires it. Without a gate, a step whose result lies outside the run folder quietly stops being performed — this has already happened twice with other checks.

Entities are taken from `refresh_targets.md` §1. No file — no entities; nothing is invented out of the prose. Claims latch onto entities already known to the wiki — the conservative direction: an unknown entity yields no pairs, an invented one yields wrong ones.

## Reading before the start

```bash
python scripts/wiki_query.py --topic "<question>"     # or --entity <name>, --stats
```

It returns: entities with past claims, sources with a ready score (do not recompute credibility from scratch), and above all — **open cross-run contradictions on the topic**. An unresolved contradiction is a ready-made research question; it goes into `plan.md` without discussion.

## Linter

```bash
python scripts/wiki_lint.py [--strict]
```

Orphans, broken `[[links]]`, edges to non-existent claims, one-sided conflicts, a stale quarantine. Run it after manually editing the registries and when drift is suspected.

## What NOT to do

- Do not edit wiki pages by hand: an edit lives until the next ingest. Anything disputed — into `pairs.jsonl`.
- Do not declare a conflict without showing both sides with their `as_of` and roots.
- Do not lower a source's `credibility` retroactively because of one run: the page accumulates the maximum score ever seen, and a divergence is a reason to look, not to silently worsen a page that others cite.
- Do not read `unknown` as «good enough» — it is quarantine, as in `authority.json`.
- Do not stay silent about the cut by `MAX_ADJUDICATED`.
- Do not set up a wiki inside a project — the point of the layer is that it is one for all researches.
- Do not gate ingest on depth.
